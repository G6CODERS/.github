# Security Policy

## Supported versions

Security fixes are applied to the default branch of each active repository. Archived repositories are not maintained.

## Reporting a vulnerability

**Do not open a public issue for a security vulnerability.**

Report it privately to **g6coders@gmail.com** with the subject line:

```text
[SECURITY] <repository> — <short description>
```

Include:

- The affected repository and branch or commit.
- A description of the vulnerability and its impact.
- Steps to reproduce, or a proof of concept.
- Any suggested fix or mitigation.
- Whether the issue is already public.

If the repository has **Private vulnerability reporting** enabled, you can also use the repository's **Security** tab → **Report a vulnerability**.

## What to expect

This is a student-run studio; we respond on a best-effort basis.

| Stage | Target |
|---|---|
| Acknowledgment | 3 business days |
| Initial triage | 7 business days |
| Critical fix | 30 days |
| Non-critical fix | Next planned release |

We will keep you informed and credit you if you want.

## Scope

This policy covers G6CODERS organization repositories and deployed applications. It does not cover third-party services, dependencies, or client systems we do not operate.

## Safe harbor

We will not pursue legal action for good-faith security research that:

- Does not access, modify, or exfiltrate data beyond what is needed to demonstrate the issue.
- Does not degrade service or disrupt other users.
- Is reported privately and given reasonable time to fix.

## Out of scope

- Social engineering.
- Denial-of-service testing.
- Automated scanning that generates significant traffic.
- Reports about outdated dependencies without a demonstrated impact.
